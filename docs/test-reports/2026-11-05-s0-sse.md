3. 腳本結束碼 0 = 全部通過;把「連線」「判定」兩段輸出貼回本檔 §3.4。

### 3.3 瀏覽器驗證(替代或補充,在 `/netops/` 頁面的 Console 執行)

同源連線,Cookie 由瀏覽器自動帶,不需複製:

```js
const es = new EventSource('/api/netops/pa-live/stream-test');
let last = Date.now();
for (const t of ['open', 'heartbeat']) es.addEventListener(t, (e) => { const now = Date.now(); console.log(new Date().toLocaleTimeString(), t, e.lastEventId, `${((now - last) / 1000).toFixed(1)}s`, e.data); last = now; });
es.onerror = () => console.warn(new Date().toLocaleTimeString(), 'error / 重連中', es.readyState);
// 結束:es.close()
```

開著 6 分鐘以上;中途在 DevTools Network 切 Offline 約 10 秒再切回,確認自動重連且 `open` 的 `resumedFrom` 為斷線前最後的 id。

### 3.4 判定項目

| # | 項目 | 通過條件 | 結果 |
| --- | --- | --- | --- |
| T1 | 不被緩衝 | 連線後 3 秒內收到 `open`;每個 heartbeat 間隔約 15 秒(最大不超過 20 秒),不是累積成一批才到 | 待驗 |
| T2 | 不受 60 秒逾時限制 | 單一連線撐過 65 秒以上(Nginx `proxy_read_timeout` 與路由逾時都是 60 秒,但都是閒置時間不是總時長);腳本另檢查最後一個事件到斷線的空窗也不超過 20 秒、事件數至少為 總時長 / 15 秒 的八成 | 待驗 |

### 3.5 斷路器與監控(T5)

- giga-observe:`netops-api` 在測試期間沒有新的 5xx / 逾時錯誤;BFF(`giga-api-gateway-bff`)沒有 `upstream: netops-api` 的「斷路器開啟」錯誤。
- 驗證期間同時開 `/netops/` 其他頁(例如流量總覽),一般 API 照常回應(斷路器沒開)。
- 參考:BFF 斷路器計入「收到上游標頭之前」的逾時與連線錯誤,以及上游回 5xx;串流已回 200 之後的中斷不計入(`bff/src/modules/router/upstream.ts`)。名額滿時本路由回 429,不計入。用戶端主動斷線只會在 BFF 日誌出現 `gw_upstream_requests_total{upstream="netops-api",outcome="2xx"}` 計數,不是失敗。

## 4. 為什麼不改 Gateway

| 關卡 | 現況(Gateway `develop` 2c0aaff) | 對 SSE 的影響 |
| --- | --- | --- |
| Nginx 緩衝 | `/api/` 沒有設定 `proxy_buffering`(預設開) | 上游回應帶 `X-Accel-Buffering: no` 時 Nginx 關閉這個回應的緩衝;BFF 的回應標頭過濾(`DROP_RESPONSE`)不含這個標頭,原樣轉送 |
| Nginx 閒置逾時 | `proxy_read_timeout 60s`(兩次讀取之間) | 心跳 15 秒,不會觸發 |
| Nginx gzip | `gzip_types` 不含 `text/event-stream` | 不壓縮,不會累積 |
| BFF 回應本體 | `reply.send(res.body)`(串流轉送,不讀完再送);只有設定快取的路由才讀完 | 本路由不設快取 |
| BFF undici 逾時 | `headersTimeout` = `bodyTimeout` = 路由逾時(預設 10 秒,本路由 `x-timeout-ms: 60000`) | `bodyTimeout` 是資料塊之間的閒置時間(§2 L6);心跳 15 秒 < 60 秒。**預設 10 秒會在第一次心跳前中斷,所以 `x-timeout-ms` 必設** |
| BFF 斷路器 | 收到標頭前的逾時與連線錯誤、上游 5xx 計入 | 串流回 200 之後的中斷不計入;名額滿回 429(不是 503),不計入 |

Gateway `docs/MONITORING-PLAN.md` 寫「不經 BFF 轉送 SSE:動態路由有逾時(x-timeout-ms),長連線會被切斷」;依上表,有心跳且心跳間隔小於 `x-timeout-ms` 時不會被切斷。測試區驗證通過後,再請 Gateway 負責人決定是否更新該段說明(本次不改 Gateway repo)。

## 5. 驗證失敗時

依 PA-LIVE-PLAN §7:改成前端每 5 秒輪詢 REST,並把失敗原因(哪一關、現象、日誌)寫在本檔與 IMPL-PLAN S0。若只是 Nginx 緩衝(T1 失敗、T2–T4 通過),可另開 Gateway MR 在 `/api/netops/` 加 `proxy_buffering off`(需求方 2026-11-05 已同意開 Gateway MR)。

## 6. 潛在風險

- 每條 SSE 佔用 BFF 到 `netops-api` 的一條 undici 連線(每個上游 128 條)與 Nginx 一條 keepalive;本路由每人 2 條、全系統 20 條。R1 正式串流要依使用人數重新評估上限,並考慮在 GigaItApp 替路由設 `keyBy: user` 的限流政策。
- 每條連線最長 10 分鐘後由伺服器結束,瀏覽器 5 秒後重連;重連時 BFF 會再檢查一次登入與權限(登出或權限移除後最多 10 分鐘內失效)。R1 的即時 log 是業務資料,要再縮短(例如對齊內部 Token 的 60 秒效期,或 1–5 分鐘),寫進 PA-LIVE-PLAN §8。
- 驗證完成後,可在 GigaItApp 停用 `netops.pa-live.stream-test` 路由,不留一個可長時間佔用連線的端點(A1、R1 參考程式仍在 repo)。
- 稽核:本路由 `x-audit-level` 為預設(不記錄);R1 的即時 log 依 PA-LIVE-PLAN §8 要設 `meta`。
