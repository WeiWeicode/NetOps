- 部署區:測試區(主機 2),容器 `giganexus-gw-bff-1-1`、`giganexus-gw-bff-2-1`;唯讀 `docker logs`,日誌範圍 2026-11-05 10:47 ~ 2026-11-10 11:39(容器啟動後)。
- 做法:只取每筆請求的方法、路徑、狀態碼、時間、`reqId`、來源位址(`incoming request` / `request completed` 兩行),未取 Token、Cookie、請求內容。
- 對照原始碼(唯讀,未修改):`giga-api-gateway-bff/bff/src/modules/auth/{routes,plugin,session}.ts`、`errors.ts`;`@giganexus/web-kit@0.3.0` `src/http.ts`;NetOps `frontend/src/composables/paLive.ts`(!51 `0c0e57e`)。
- 背景:GigaItApp「架構觀測 › 錯誤」近 7 天 `POST /api/auth/refresh` 403 共 10 次(最後約 2026-11-10 10:40)、`GET /api/auth/me` 401 共 62 次。

## 2. 結果

**結論:403 是 CSRF 驗證失敗(`CSRF_INVALID`),發生在「瀏覽器已沒有登入 Cookie」的時候;不是 Refresh Token 輪替的併發問題,也不是 !51 造成的。**

BFF 日誌中 `POST /api/auth/refresh` 共 55 筆:200 共 50 筆、403 共 5 筆(每日:11-05 200×5;11-09 200×15、403×2;11-10 200×30、403×3)。

### 2.2 為什麼是 CSRF 而不是 Refresh Token 失效

- BFF `routes.ts` 的 Refresh Token 失效(`reused` / `expired` / `missing`)一律丟 `REFRESH_TOKEN_INVALID`,`errors.ts` 對應 **401**;403 只可能是 `CSRF_INVALID`(`errors.ts:49`)。
- `/api/auth/refresh` 不在 `CSRF_EXEMPT`(`plugin.ts:41`),非 GET 的 `preHandler` 要求 `X-CSRF-Token` 等於 `gn_csrf` Cookie(`session.ts` `csrfValid`)。
- web-kit `refreshSession()` 的 `csrfHeader()` 在 `gn_csrf` Cookie 不存在時**不帶標頭**(`http.ts:49-51`)→ BFF 回 403。
- `gn_csrf` 與 `gn_rt` 同壽命(`session.ts:92-97`,`maxAge = rtMaxAge`),登出或換發失敗時 `clearCookies` 一併清除。所以「沒有登入 Cookie」(從未登入、登入逾時、已登出、另一分頁登出)時,頁面載入 → `me` 401 → `refreshSession()` → 沒有 CSRF → 403 → 導向登入,是目前程式的正常路徑,不是故障。13:49:22 那筆正好在 `logout` 後 1 秒,10:39:56 那筆 6 秒後使用者重新登入,都符合。
- 10:39:30 那筆之後 2.5 秒仍有 `snapshot` 200:同一出口位址(10.10.112.13,各請求來源位址都是它,無法分辨個別瀏覽器)可能是不同瀏覽器 / 分頁;日誌沒有記 User-Agent 與 Cookie,**無法再往下確認是哪一個用戶端**。

### 2.3 併發換發檢查(需求方的假設)

- 全部 55 筆 refresh 中,間隔小於 1.5 秒的只有 2 組,**兩組都是 200 / 200**:11-10 11:06:38.629 / 11:06:39.428、11:35:09.489 / 11:35:09.518。沒有「第二個用舊 Token 被拒」(那會是 401 `REFRESH_TOKEN_INVALID` 並在 `auth_log` 留 `token_reuse_detected`)的跡象。
- web-kit `refreshSession()` 以 `refreshing` Promise 單飛(同一頁面多個 401 共用同一次換發,`http.ts:38-46`);!51 的串流 401 也呼叫同一個 `refreshSession`(`paLive.ts`),沒有另開換發路徑。併發只可能發生在**不同分頁**之間(各自單飛),上述兩組就是這種情形,結果都成功。
- `me` 401 共 38 筆,其中 12 筆在 1 秒內接著 refresh(Access Token 15 分鐘到期的正常換發,`ACCESS_TTL_SEC = 15 * 60`),其餘 26 筆 `me` 401 後 1 秒內沒有 refresh(可能是不同分頁的 refresh 稍後才到、或用戶端已放棄,未逐一確認)。

### 2.4 與觀測畫面數字的差異

觀測畫面 refresh 403 共 10 次、`me` 401 共 62 次;兩個 bff 容器日誌只有 5 次與 38 次(日誌只到 11-05 容器啟動為止,且以 `request completed` 計)。差異可能來自:觀測以 Nginx 或 7 天視窗計算、容器重建前的日誌已不在、或另有 BFF 之外的來源。**未查明**;不影響根因判斷(同一個錯誤代碼路徑)。

## 3. 失敗項目

- 無測試失敗;本次是日誌調查,未改任何程式。

## 4. 可能問題

1. **沒有登入 Cookie 時 web-kit 仍呼叫 `refreshSession()`**:必然得到 403 並在觀測留下錯誤。位置:`@giganexus/web-kit` `src/http.ts` `refreshSession()` / `request()` 的 401 分支(屬 `giga-api-gateway-bff` repo)。
2. BFF 對「Refresh 缺 CSRF」回 403 而不是 401:語意上是「沒有可換發的登入狀態」,與 `REFRESH_TOKEN_INVALID`(401)不一致,監控會把正常的登入逾時算成 403 錯誤。位置:`bff/src/modules/auth/plugin.ts` CSRF `preHandler`。
3. NetOps 前端沒有自己的換發邏輯,全部走 web-kit;**NetOps 程式不需修改**,沒有開 `fix/auth-refresh-403`。

## 5. 建議(交給 Claude / 需求方)

- 在 `@giganexus/web-kit` `refreshSession()` 加一行:`gn_csrf` Cookie 不存在時直接回 `false`(不送請求),即可消除這類 403;或 BFF 對 `/api/auth/refresh` 缺 CSRF 回 401 `REFRESH_TOKEN_INVALID`。兩者擇一(前者較小、不動 API 契約)。**這兩處都在 `giga-api-gateway-bff` repo:不在本任務範圍,需要需求方同意另開任務。**
- 觀測畫面的「錯誤」可把此情境(`me` 401 → `refresh` 403 → 登入)視為已知的登入逾時雜訊,修正前不需追查。
- 不需要處理併發換發。需要追查個別用戶端時,要在 BFF 日誌加 User-Agent(屬 Gateway repo,同樣需另開任務)。
