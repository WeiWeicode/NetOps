## 3. 失敗項目

最終版本沒有失敗。過程中出現過、已處理的:

- 第一次 `test:int`:既有 `archive.int.test.ts`「排程一輪…」`15 !== 14`。原因是新的 AD 歸檔測試在同一天寫了 `ad` 的 manifest,這個斷言數的是所有種類。**改成只數 PA 的種類**(`ARCHIVE_KIND_LIST.includes(x.kind)`),檢查的強度不變(PA 7 種 × 2 天都要 ok),不是放寬。
- 單元測試初版有 3 個是測試本身寫錯(預設參數吃掉 `undefined`、`text/plain` 會被 Fastify 解析成字串、模擬 ACK 失敗的寫法),修正測試寫法,沒有改變要驗證的行為。

## 4. 可能問題

- **完成標準「部署只重建 `netops-ad-receiver` 時 `netops-pa` 不重啟、PA Syslog 不中斷」還沒驗證**:要在測試區部署後看(`deploy/RUNBOOK-ad.md` §2 第 5、6 步)。本機已確認 Compose 中 `netops-pa`、`netops-redis` 的服務定義與 `pa-ingress`、`netops-internal` 網路**和 develop 完全相同**(YAML 解析後比對),CI 對 receiver 用 `up -d --no-deps --force-recreate`;CI 在判斷 `netops-pa` 之前先檢查 `ad_agent_tokens`,避免缺檔時誤判成要重建。
- **Compose 定義了 `ad_agent_tokens` secret**:主機上沒有這個檔時 compose 指令可能失敗(RUNBOOK-prod 第一段就有同樣的說法)。合併前兩台主機都要先執行 `host2/3-set-ad-secrets.sh add`(MR 描述第一行)。
- **Redis 沒有 AOF**:`netops-redis` 當機時,快照之後的 Stream 與水位會遺失,Agent 已收到 200 的事件不會重送;要靠 AD-3 的 FTP 對帳補漏(已寫進 RUNBOOK-ad §5)。
- **水位可被持有 Token 的人灌到極大值**:之後該台 DC 的正常事件都會被當成重複(資安審查 M1 的一部分)。已加每分鐘請求上限;RecordID 跳躍上限沒有做(Security 的 RecordID 包含未收集的事件,長時間離線後的正常跳躍可能很大,門檻需要 AD-2 實測後決定)。
- 本機 Redis 用 `redis:7-alpine`,CI 是 `redis:7.4-alpine`;Lua 只用基本指令(`XADD MINID` 需要 6.2+)。
- 較慢的既有單元測試:「API:NETOPS_AI_SOURCE=clickhouse」約 9.5 秒、「ClickHouse 資料來源:長期間 fixture」約 7.6 秒(和本批無關)。

## 5. 建議的處理項目

1. 測試區部署後依 `deploy/RUNBOOK-ad.md` §2 第 6 步記錄 `netops-pa` 的 `StartedAt` 與 `syslogOkAt`,補到本報告或 MR。
2. AD-2 實測 Security RecordID 的正常跳躍量後,決定是否加 RecordID 跳躍上限。
3. AD-3 設計 FTP 對帳時,把「Redis 遺失」的缺口納入補漏範圍。
4. AD-5 / 前端顯示心跳 `data` 與 Watchdog 事件時當不可信資料處理。
