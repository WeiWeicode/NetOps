## 3. 失敗項目

最終版本沒有失敗。過程中:
- 新增的 Watchdog 測試初版用了不存在的 `Monitor::default()`(編譯錯誤),改用 `Monitor::new(T)`;測試要驗的行為沒變。

## 4. 可能問題

- **兩個服務以 LocalSystem 執行**(讀 Security Log、控制 SCM 需要;需求方已接受)。Agent 被攻破等同 DC 上的 SYSTEM;改 gMSA / 虛擬帳號在 DC 上設定複雜,未做。
- **Redis 沒有 AOF**:Agent 收到 200 就前進水位,`netops-redis` 當機時快照之後的事件遺失,靠 AD-3 FTP 對帳補漏(同 AD-1 報告)。
- **RecordID 跳號上限還沒定**:接收端沒有限制單次 RecordID 跳躍,持有 Token 的人送極大 RecordID 會讓之後的正常事件被當成重複。上限要等 §7.2 實測正常跳躍量後再定。
- **執行檔只驗 SHA-256,沒有 Authenticode 簽章**:雜湊與 exe 出自同一個 pipeline,擋不住「tag 本身是惡意的」。已改成只有 `netops-ad-v*` tag 產出 artifact,並要求設為 Protected tag;是否接 RustIt S1 簽章流程由需求方決定。
- **`host2-windows` Runner 目前只指派給 RustIt**:`check:ad-agent` / `build:ad-agent` 在 NetOps 不會執行,需求方要在 GitLab 指派。
- **`bookmarks.json` 遺失 + 停機期間清除過 Security Log + 清除後的新事件已超過舊水位 R**:`resolve_initial` 無法分辨,會沿用舊世代從 R 之後接著讀,新世代的 1..R 不會送(由 AD-3 對帳補)。三個條件同時成立才會發生。
- **確定性 4xx(400 / 413)仍會無限重送同一批**:現在心跳有 `sendRejectStreak` 與範圍,但沒有自動拆批;要靠 V-c 規則 10 告警與人工處理。
- **XML 無法解析的事件水位會越過**(只計數 `skippedEvents`,不分暫時 / 永久錯誤),由 AD-3 對帳補。
- **單一 Event Log / HTTP 呼叫卡住超過 90 秒才算停止回應**:每個阻塞呼叫前都更新單調時鐘,一輪內多個呼叫各自逾時累加不會誤殺;單一呼叫卡死仍會被重啟(設計如此)。
- ~~接收端 `watermarks()` 讀 Redis 失敗時回 `{}`~~(**已解決**:`9ed7a9c` 改回 `503 NETOPS_AD_UNAVAILABLE`,`ad71a82` 補 Agent 收到 503 時不決定起點、恢復後照後端世代接續的測試)。
- 審查的 Low 項目未修(管道名稱被搶先佔用、Watchdog 連管道未設 `SECURITY_IDENTIFICATION`、`restarts24h` 實為 10 分鐘視窗、冷卻中只上報一次 `agent_start_failed`、`TerminateProcess` 後立即 `StartService` 的競態、管道伺服端讀取無逾時、停止時未回報 `StopPending`、`log_dir` / `state_dir` 接受絕對路徑、移除時 `Remove-Item -Recurse` 遇 junction)。
- `npm test` 較慢的既有測試(與本批無關):`API:NETOPS_AI_SOURCE=clickhouse` 約 17 秒、`Archiver.tick` 約 17 秒、`PA 即時監控串流(SSE)` 約 14 秒。
- 腳本測試在 Git Bash 下輸出亂碼(主控台編碼),不影響結果。
