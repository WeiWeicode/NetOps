## 4. 可能問題

**CSV 補寫列與 Agent 列的差異**(`ad3.int.test.ts` 實測):
- **相同**:`event_time`(兩者都到秒,`DateTime('Asia/Taipei')`;Agent 的毫秒在寫入時捨去)、`level`、`account`、`src_ip_raw` / `src_ip`、`workstation`、`reason`、`is_issue`、`message`、`log_epoch`。
- **不同**:`level_text`,CSV 是 DC 語系的中文(「稽核失敗」),Agent 是英文(`Audit Failure`)。只影響畫面上的原文等級文字,`level` 相同。另 `received_at` 是補寫時間。
- **前提**:DC 時區是台北時間(CSV 沒有時區,以 +08:00 解析)。`Message` 實測用的是同一份文字;Agent 的 `EvtFormatMessage` 與 CSV 的 `$_.Message` 在 DC 上是否逐字相同,**要等 GSMC-DC1 實機資料才能確認**(建議項目 1)。

**審查發現與處理**:
- code-reviewer H1(忙碌記錄 RecordID 與時間小幅倒序,被誤切成假段 → `ambiguous` 永遠補不上):切段改為「比段內最大值小超過 10,000」或「小於段內最小值的一半」才切。已修正並加測試。
- code-reviewer M2 / security-auditor M1:水位原本採信 Redis 接收端水位。它在收到時就前進,事件可能還在 Stream,先補會重複;`netops-redis` 沒有 ACL,竄改後缺口永遠補不回。改為**只採信 ClickHouse 已寫入的 Agent 最大 RecordID**。已修正。
- code-reviewer M4(對帳與補漏的去重鍵不同):補漏改用和匯入器相同的鍵(DC、記錄、RecordID)。
- code-reviewer M5(ambiguous / waiting 的列讓自動補漏每天重送):上一次還在跑、或做完 0 筆且缺口沒變時不重送。
- security-auditor M2(失敗原因含 `'` 時總覽查詢可能失敗):改為每個原因一個 `String` 參數;整合測試加含 `'` 與 `\` 的原因。
- security-auditor L3(補漏錯誤訊息帶 FTP 路徑)改固定文字;L6(`POST /ad/reconciliations` 稽核)設 `meta`。
- **未修正、列為後續**:
  - code-reviewer M3:DC 名稱寫法。RUNBOOK 已註明 Token 對應表寫大寫短名。
  - code-reviewer M6:`NETOPS_AD_SOURCE=ftp` 時,只要有 ClickHouse 設定仍會對帳與自動補漏。這是刻意的,切換前先把資料補齊;RUNBOOK 已註明關閉方式。
  - code-reviewer Low 13:prev 不成立時不再試 next。這是保守做法,D1 已同意 `ambiguous` 不寫。
  - security-auditor 5(總覽查詢負載,92 天、11 支查詢):有 `max_execution_time` 與唯讀帳號限制。
  - security-auditor 6:`netops.ad.read` 也綁在 PA AI 按鈕,只有 PA 權限的人也看得到 DC 狀態。屬既有 `gateway-rbac.yaml`,需求方確認。

**剩餘風險**:
- **Agent 長期離線**(D5):`waitingAgent` 的列一直不補,直到 Agent 恢復並送出,或 FTP 超過保留期限。這期間 ClickHouse 缺這些事件。若 Agent 永久不再運作(未正式除役),FTP 也不會補。
- `ambiguous`(Agent 停機期間 Security Log 被清除、清除前後沒有對得上的 Agent 列)的列不寫入,只記 warn,要人工處理。
- 未裝 Agent 的 DC,一天內清除重編號時,兩段都用世代 0。極少數 RecordID 相同的列會被當成已存在而略過(兩個世代的 RecordID 要剛好重疊,實務上不太可能)。
- 對帳結果不存檔(即時計算);`backfills` 只記本次程序啟動後建立的工作(工作本身在 Redis 保留 7 天)。
- 前端 vitest 輸出 `ECONNREFUSED 127.0.0.1:3000`(既有,測試仍通過,和本批無關)、vite build chunk > 500 kB 警告(既有)。

## 5. 建議的處理項目

1. GSMC-DC1 實機:同一天比對 FTP CSV 與 Agent 的 `Message` 是否逐字相同,並確認 DC 時區。
2. 測試區合併部署後:看第一次 08:10 AD 對帳結果(`GET /api/netops/ad/reconciliations`),依 RUNBOOK-ad §8 判讀;需要時切 `NETOPS_AD_SOURCE=clickhouse`(只重建 netops-api)。
3. netops-redis 加 ACL(netops-pa 只給 `netops:pa:*`),長期降低 Redis 被竄改的風險(資安審查 M1 的根本處理,跨 AD-1 範圍)。
4. 前端(Gemini):依 MR「後續 › 前端交接」實作三個畫面。
